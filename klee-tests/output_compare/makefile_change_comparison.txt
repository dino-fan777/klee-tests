==============================================================================

Generated by running every suite twice against the same compiled .bc files,
under two different Makefile pass/fail RULES (the test .c files and the KLEE
binaries themselves were NOT changed between the two runs):

  BEFORE (old rule):
    FAIL if "completed paths = 0"                        OR
    FAIL if the log contains "KLEE: ERROR" ANYWHERE (even on a single
         side path that was never meant to be the one under test)
    PASS otherwise

  AFTER (current rule, matches the professor-approved criterion):
    FAIL only if "completed paths = 0"
         (i.e. no input exists that satisfies the __assume()s AND makes it
          all the way through every __gen_assert() to a clean exit)
    PASS otherwise — it no longer matters if OTHER, unrelated symbolic
         paths hit an error, as long as at least one full path is clean.

This is an EXISTENTIAL criterion ("does a satisfying input exist") replacing
what was accidentally a UNIVERSAL criterion ("does every explored path have
to be clean"). The old rule was strictly stronger / stricter than what was
actually being asked for, so PASS(before) implies PASS(after) in every case
with zero exceptions confirmed below — the change can only turn a FAIL into
a PASS, never the reverse.

WHY THE RESULTS CHANGED
==============================================================================

1) 46 tests FLIPPED from FAIL to PASS
------------------------------------------------------------
Every single flipped test has the SAME root cause: the test's main symbolic
path completes cleanly (completed paths >= 1) and every __gen_assert() on
that path holds. But because fname[0] is symbolic over the full domain KLEE
explores (not just the letters bound to actual sym-files), and/or flags is
fully symbolic before being pinned with __assume(flags_equal(...)), KLEE
also forks side paths where an unrelated __gen_assert() cannot be PROVEN
true for every possible symbolic value on THAT side path. Those side paths
report:

    KLEE: ERROR: klee_src/runtime/POSIX/file_api.c:181: assertion is not
    necessarily true

...and terminate as error paths (so they never contribute to "completed
paths"). Under the old rule, that single line anywhere in the log failed
the whole test even though the path actually being tested was fine. Under
the current rule, only completed-path count matters, so these tests now
correctly PASS. Affected tests (suite: test list):

  chmod  : test_01, test_04, test_05, test_08, test_09, test_12, test_13
  open   : test_02, test_03, test_04, test_10, test_11, test_17, test_18, test_19, test_28, test_30, test_38, test_39, test_41, test_42, test_43, test_44, test_46, test_49
  close  : test_02, test_07
  dup    : test_10, test_11
  lseek  : test_13, test_14
  read   : test_02, test_03, test_10, test_11, test_12
  write  : test_01, test_02, test_04, test_05, test_06, test_08, test_09, test_10, test_11, test_12

2) 19 tests STILL FAIL — assertion never provably true on ANY path
------------------------------------------------------------
These have completed paths = 0 under BOTH rules: every symbolic path KLEE
explores hits the same
    KLEE: ERROR: klee_src/runtime/POSIX/file_api.c:181: assertion is not
    necessarily true
error — there is no input at all for which every __gen_assert() in the
test can be proven to hold. This is not an artifact of the Makefile change;
it was a FAIL before and remains a FAIL after, and is worth auditing —
either the test's __assume()s under-constrain the scenario (so KLEE finds
a symbolic counter-example the test didn't anticipate), or it is catching a
real discrepancy between the expected and modeled syscall behavior.
Affected tests:

  chmod  : test_03, test_06, test_07, test_10, test_11
  open   : test_12, test_24, test_25, test_26, test_27, test_29, test_31, test_33, test_34, test_35, test_36, test_45
  lseek  : test_15
  write  : test_13

3) 6 tests STILL FAIL — genuine memory-safety error (different from #2)
------------------------------------------------------------
All 6 are in open/. Unlike the assertion failures above, these hit a KLEE
memory-safety error, not an assertion:

    KLEE: ERROR: klee_src/runtime/POSIX/fd_32.c:74: memory error: out of
    bound pointer

This means the test drives open() (or the surrounding POSIX runtime code
in fd_32.c) into dereferencing a pointer outside its allocated bounds on
every explored path — a materially more serious finding than an unprovable
assertion, since it indicates an actual out-of-bounds access in the fd
layer rather than a property the test merely couldn't confirm. This is the
same class of finding the old open()-suite Makefile comments called out as
"maybe bug?" and deserves priority triage over the assertion-only failures
above. Affected tests:

  open   : test_07, test_08, test_09, test_15, test_16, test_22

==============================================================================
METHODOLOGY NOTES / CAVEATS
==============================================================================

- __gen_assert() as actually compiled in klee_fork/runtime/POSIX/file_api.c
  (line 198-201) at the time of these runs is still the klee_is_certain()-
  based implementation:

      void __gen_assert(cnstr_t expr){
         if ((klee_is_certain(_NOT_(expr))))
            __report_error(__FILE__, __LINE__, "assertion is not necessarily true");
      }

  This is NOT the klee_assert()-based version discussed earlier in this
  session. If you intended that swap to already be live, the runtime needs
  to be rebuilt/relinked before re-running this comparison — the error text
  above would change from "assertion is not necessarily true" to something
  matching klee_assert()'s own "ASSERTION FAIL: ..." wording, and the exact
  file:line would move to wherever klee_assert's macro expands from.

- The old-vs-new comparison used the exact same compiled .c test files and
  the exact same KLEE binary invocation for both runs — only the Makefile's
  post-hoc grep over the log text differed. No test source was recompiled
  between the two runs.

- Zero tests regressed (PASS-before -> FAIL-after) in any suite, which is
  the expected mathematical consequence of the new rule being strictly
  weaker than the old one (see criterion definitions above) — included here
  as a sanity check that the Makefile edit didn't silently break anything.

- The current ("after") rule is intentionally weaker: it only asks whether
  a SINGLE satisfying input exists, matching the professor's stated
  criterion. It is not evidence that every explored branch is bug-free —
  the STILL-FAIL tests above (and any suite-wide 'KLEE: ERROR' on a
  non-completed path even in a PASSing test) can still be worth reading
  individually if the goal is bug-hunting rather than pass/fail grading.
